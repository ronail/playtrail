# Playtrail

An append-only move log API for turn-based board games.

Clients upload batches of actions. Playtrail stores each batch as an immutable
object, and storage deletes it 14 days after upload. No database, no business
logic, no conflict resolution. Designed to cost about $0 at low volume on
Cloudflare Workers + R2.

> **Status: v1.** Verified against a real R2 bucket, except that the 14-day expiry
> has not been observed yet. See the [PRD](docs/PRD.md) and [TRD](docs/TRD.md).

## How it works

```
GET  /v1/challenge                     → { challenge }   (Android)
POST /v1/register + proof              → { client_id, key }
PUT  /v1/logs/{client_id}/{batch_id}   → 201 stored | 200 already stored
```

- The body is NDJSON, one action per line, up to 32 KB.
- Web players register by signing in with Google; the same account always gets
  the same `client_id`. There is no user database, and names and emails are not
  stored. Android registers with Play Integrity.
- Each upload is signed with the key from registration (HMAC-SHA256).
- `batch_id` is generated by the client, so retries don't duplicate data.
- Every batch expires 14 days after upload, even for active players. Export
  anything you want to keep.

### Example

One batch:

```json
{"seq": 41, "ts": "2026-11-24T10:00:00Z", "type": "tile_discarded", "data": {"seat": 2, "tile": 17}}
{"seq": 42, "ts": "2026-11-24T10:00:09Z", "type": "turn_ended", "data": {"seat": 2}}
```

Upload it:

```
PUT /v1/logs/7f3c…/01JDQ8… HTTP/1.1
Content-Type: application/x-ndjson
X-Signature: base64(HMAC-SHA256(key, client_id + "\n" + batch_id + "\n" + body))
```

`register` returns `key` as base64. **Decode it first:** the HMAC key is the
decoded bytes, not the base64 text. Use `https://`: plain HTTP gets 403, except
on localhost. IDs are 1 to 64 characters from `A-Z`, `a-z`,
`0-9`, `_` and `-`; a ULID or UUID works as a `batch_id`.

### Client example

In a web game, sign the player in with
[Google Identity Services](https://developers.google.com/identity/gsi/web) and
register with the ID token it returns:

```js
google.accounts.id.initialize({
  client_id: "<GOOGLE_CLIENT_ID>",
  callback: async ({ credential }) => {
    const res = await fetch(`${base}/v1/register`, {
      method: "POST",
      body: JSON.stringify({ google_id_token: credential }), // accepted for 300 s
    });
    const { client_id, key } = await res.json(); // store both
  },
});
google.accounts.id.renderButton(document.getElementById("signin"), {});
```

A Godot web export can run this through `JavaScriptBridge`: export
single-threaded and do not send `Cross-Origin-Opener-Policy` or
`Cross-Origin-Embedder-Policy` headers.

To try it from a shell, save as `client.mjs` and run with `node client.mjs`
(Node 20 or later). Set `BASE_URL` to your deployment and `GOOGLE_ID_TOKEN` to a
token your client ID issued in the last 300 s.

```js
const base = process.env.BASE_URL ?? "http://localhost:8787";
const enc = new TextEncoder();

// Once per install, then store both values.
const { client_id, key } = await (
  await fetch(`${base}/v1/register`, {
    method: "POST",
    body: JSON.stringify({ google_id_token: process.env.GOOGLE_ID_TOKEN }),
  })
).json();

const hmacKey = await crypto.subtle.importKey(
  "raw",
  Uint8Array.from(atob(key), (c) => c.charCodeAt(0)), // decoded bytes
  { name: "HMAC", hash: "SHA-256" },
  false,
  ["sign"],
);

// Once per batch: reuse batch_id and body on every retry.
const batchId = crypto.randomUUID();
const body = JSON.stringify({ seq: 1, ts: new Date().toISOString(), type: "turn_ended", data: {} }) + "\n";
const mac = await crypto.subtle.sign("HMAC", hmacKey, enc.encode(`${client_id}\n${batchId}\n${body}`));

const res = await fetch(`${base}/v1/logs/${client_id}/${batchId}`, {
  method: "PUT",
  headers: {
    "Content-Type": "application/x-ndjson",
    "X-Signature": btoa(String.fromCharCode(...new Uint8Array(mac))),
  },
  body,
});
console.log(res.status); // 201 stored, 200 already stored
```

Keep the batch until you get 201 or 200. See the
[status codes](docs/TRD.md#put-v1logsclient_idbatch_id) for the rest.

## Deploy

You need Node 22 or later and a Cloudflare account with R2 enabled.

```sh
npm install
npx wrangler login
npx wrangler r2 bucket create playtrail-logs
npx wrangler r2 bucket lifecycle add playtrail-logs --name expire-14d --expire-days 14
npm run deploy
openssl rand -base64 32 | npx wrangler secret put MASTER_KEY
```

Requests fail with 500 until `MASTER_KEY` is set. Keep it random, as generated
above: anyone who registers can brute-force a guessable one. Then set a billing
notification in the Cloudflare dashboard, keep the bucket private, and give
readers a read-only R2 token.

### Google sign-in (web)

In Google Cloud, set up the OAuth consent screen and create an OAuth client of
type **Web application**. Add your game's HTTPS origin (and
`http://localhost:<port>` for development) as authorized JavaScript origins.
Then give the Worker the client ID:

```sh
npx wrangler secret put GOOGLE_CLIENT_ID
```

Without it, Google sign-in is refused. The token also carries the player's name,
email and picture; the Worker neither stores nor logs them. Logs are filed under
a stable pseudonymous ID, so publish a privacy policy and show players their
`client_id` for erasure requests.

### Release key (CI only)

CI cannot sign in to Google, so it registers with an Ed25519 key. Make a pair:

```sh
node -e 'const j=require("crypto").generateKeyPairSync("ed25519").privateKey.export({format:"jwk"});const b=v=>Buffer.from(v,"base64url").toString("base64");console.log("private seed:",b(j.d),"\npublic:",b(j.x))'
```

Store the seed as the `BUILD_SEED` secret (see [CI](#ci)) and the public key in
the Worker. Never commit the seed or ship it in a build.

```sh
npx wrangler secret put BUILD_KEYS   # {"ci":"<public>"}
```

### Play Integrity (Android)

The app must be in Play Console and linked to a Google Cloud project with the
Play Integrity API enabled. Create a service account in that project, then set:

```sh
# Redirect the file: the prompt takes one line, and the key spans many.
npx wrangler secret put GOOGLE_SA_KEY < /path/outside/the/repo/service-account.json
npx wrangler secret put ANDROID_APPS    # {"com.example.game":["<certificate SHA-256 digest>"]}
```

Never commit the key. The digest is the one Play reports in
`certificateSha256Digest` (base64url of the app signing certificate's SHA-256).
Local and debug builds are not expected to pass: test through a Play internal
test track. Without both secrets, Android cannot register. The request format is
in the [TRD](docs/TRD.md#post-v1register).

### Rate limits

Defaults are 5 registrations per IPv4 address or IPv6 /64 and 10 uploads per client, each per 60
seconds. To change either, set `REGISTER_LIMIT` or `UPLOAD_LIMIT` (a positive
whole number) in the shell that deploys:

```sh
REGISTER_LIMIT=20 UPLOAD_LIMIT=60 npm run deploy
```

The limits are fixed at deploy time, so setting them as Worker variables does
nothing. Each deploy applies only what is set then: a later one without them goes
back to the defaults. `npx wrangler deploy` ignores them. `npm run dev` and
`npm test` honour them too. The 60 second period is not configurable here
(Cloudflare allows only 10 or 60). For CI, see [CI](#ci).

## Develop

```sh
echo "MASTER_KEY=local-only-key" > .dev.vars
echo 'GOOGLE_CLIENT_ID=<client ID>' >> .dev.vars       # see Google sign-in
npm run dev      # http://localhost:8787
npm test         # starts its own server; stop `npm run dev` first
npm run check    # type check
BASE_URL=https://your-worker.workers.dev BUILD_ID=ci BUILD_SEED=... npm test   # against a deployment
```

Plain HTTP is accepted only for `localhost`, `127.0.0.1` and `[::1]`. From an
Android emulator or device, run `adb reverse tcp:8787 tcp:8787` and use
`http://localhost:8787`, not `10.0.2.2` or a LAN address.

A run against a deployment waits and retries when it hits a rate limit, so it can
take a few minutes with low limits or right after another run.

## CI

[The workflow](.github/workflows/ci.yml) runs the type check and local tests on
pull requests to `main`. On a push to `main` (including a merge) it also deploys
and runs the tests against the deployment. A failed test does not roll the
deployment back.

It needs the one-time setup under [Deploy](#deploy) (bucket, lifecycle rule,
`MASTER_KEY`, and a `ci` entry in `BUILD_KEYS`) and these repository settings. Nothing about your account is committed.

| Name | Kind | Value |
|---|---|---|
| `CLOUDFLARE_API_TOKEN` | secret | A custom API token for your account with **Workers Scripts: Edit**, **Workers R2 Storage: Read** and **Account Settings: Read** |
| `CLOUDFLARE_ACCOUNT_ID` | variable | Your account ID (`npx wrangler whoami`) |
| `BUILD_SEED` | secret | Private seed of the `ci` release key. Whoever has it can register |
| `BASE_URL` | variable | Your deployment with no trailing slash, such as `https://playtrail.example.workers.dev` |
| `REGISTER_LIMIT` | variable, optional | Registrations per IPv4 address or IPv6 /64 per 60 s (default 5) |
| `UPLOAD_LIMIT` | variable, optional | Uploads per client per 60 s (default 10) |

```sh
gh secret set CLOUDFLARE_API_TOKEN   # paste at the prompt
gh variable set CLOUDFLARE_ACCOUNT_ID
gh variable set BASE_URL
gh secret set BUILD_SEED             # paste at the prompt
gh variable set UPLOAD_LIMIT --body 60       # optional
gh variable delete UPLOAD_LIMIT              # back to the default
```

A changed limit applies at the next deploy, not when you set it. An invalid value
fails the deploy step, leaving the previous deployment in place. The `test` job
(pull requests and pushes) always uses the defaults.

Variables are not masked, so the account ID and URL can appear in this public
repo's run logs. Use secrets instead if that matters.

Each run against the deployment leaves a few test objects, which expire with the
rest.

## What it is not

- Not a multiplayer sync server: no read API, match grouping or move validation.
- Not an analytics dashboard: you read the files straight from your bucket.
- Not audit-grade: a client can send whatever it likes under its own ID.
- Not abuse-proof: anyone with a Google account can register, and one person can
  have many. Limits don't stop a determined attacker. See [Security](docs/TRD.md#security).
